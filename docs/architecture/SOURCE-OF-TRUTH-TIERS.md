# Source-of-Truth Tier Hierarchy

Status: current as of 2026-08-22. This is deliberately one short document, not a new layer of bureaucracy: its only purpose is to state, once, which sources override which, so old information stops resurfacing as though it were current.

## The 4 tiers

**Tier 1: Founder-confirmed current decisions.** Anything Anthony has directly confirmed in the current conversation or a dated, current instruction. Overrides every other tier automatically, including this document's own defaults.

**Tier 2: Canonical/current operating and financial models.** `docs/CURRENT-STATE.md`, `data/canonical/*.yml`, `data/models/master_financial_model.yml`, and the specific architecture documents those files cite as their own current basis (for example `docs/architecture/DEMAND-DRIVEN-STAFFING-MODEL.md`, `docs/architecture/STAFFING-COVERAGE-VALIDATION.md`, `docs/architecture/FIT-OUT-PROGRAM-DECISION-ANALYSIS.md`). These are authoritative for any figure, headcount, or program decision unless a Tier 1 instruction has directly superseded them.

**Tier 3: Current strategic reports.** Investigation and research documents that are dated and still current (for example this session's `docs/architecture/MARKET-RESEARCH-BIRTHS-GDM-REFERRAL-2026.md`, `docs/architecture/VENUE-PROGRAM-AUTHORITATIVE.md`). These inform Tier 2 documents but do not themselves override a Tier 2 figure without that figure being updated to match.

**Tier 4: Supporting research.** Everything else in `docs/` and `docs/architecture/` not listed above. Treated as historical/stale unless a specific document is explicitly revalidated and promoted into Tier 2 or Tier 3 by a dated changelog entry.

## The rule

If a Tier 4 document contradicts a Tier 2 or Tier 3 document, the Tier 4 document is stale. The correct action is to update the Tier 4 document itself (or mark it superseded in its own changelog) so it stops contradicting current truth, not to keep disclosing the contradiction every time the topic comes up in the dossier or Dash. The Master Dossier and Dash draw only from Tier 1-3; Tier 4 documents should not be cited as a current source in either.

## What this replaces

Before this document, current-state governance was implicit: `docs/CURRENT-STATE.md` was understood as authoritative but nothing stated the tier relationship for architecture-level research documents versus older strategy documents versus one-off investigation notes. This caused the same historical contradiction (old property listings, old staffing figures, old pricing methodology, spray tan, the GDM snack pack) to be re-discovered and re-disclosed in the dossier repeatedly across sessions instead of being fixed once at the source.

## Procurement Source-of-Truth (added 2026-08-23, Part 15)

For every procurement question below, exactly one document wins if two disagree. This does not create a new tier; `MASTER-PROCUREMENT-SHOPPING-LIST.md` sits at Tier 2 (a canonical current operating document) per the tiers above, and every other procurement document listed here is subordinate to it, generated from it, or explicitly scoped to a narrower question it does not itself re-decide.

| Question | Authoritative document | Why |
|---|---|---|
| Item identity (does this item exist, what is its Procurement ID) | `docs/architecture/MASTER-PROCUREMENT-SHOPPING-LIST.md` | The only document that assigns Procurement IDs; every other procurement document references an ID from here, none invents a new one. |
| Quantity | `docs/architecture/MASTER-PROCUREMENT-SHOPPING-LIST.md` | Explicitly restated as the rule in `PROCUREMENT-ROOM-BY-ROOM-CHECKLIST.md` and `PROCUREMENT-ITEM-SPECIFICATIONS-FULL.md`: neither restates quantities as an independent figure, both look the quantity up from here. |
| Specification (what to look for, dimensions, material, finish) | `docs/architecture/MASTER-PROCUREMENT-SHOPPING-LIST.md`'s Description/Specification column, expanded (not contradicted) in `docs/architecture/PROCUREMENT-ITEM-SPECIFICATIONS-FULL.md` | The Full Specifications document is generated mechanically from the register's own text; it cannot disagree with it by construction. |
| Sourcing route (China/Australia/Hybrid/Professional/WDP/Site) | `docs/architecture/MASTER-PROCUREMENT-SHOPPING-LIST.md`'s Sourcing column | `PROCUREMENT-CHINA-PACKAGE.md` and `PROCUREMENT-AUSTRALIA-PACKAGE.md` group items by this existing classification; neither reclassifies an item independently. |
| Price | `docs/architecture/MASTER-PROCUREMENT-SHOPPING-LIST.md`'s Notes/Status columns, where a Status of "Priced" exists | No procurement document invents a price not already in the register; `PROCUREMENT-ITEM-SPECIFICATIONS-FULL.md`'s "Existing price/source" field explicitly states "No price researched yet" where the register itself has none. |
| Readiness (A-H classification) | `docs/architecture/MASTER-PROCUREMENT-SHOPPING-LIST.md`'s Readiness column | `PROCUREMENT-ORDER-READINESS-CHECKLIST.md` is explicitly built to reuse this classification, stated in its own preamble as "not a second, conflicting status system." |
| Opening stock quantity (actual sized figure) | `docs/architecture/PROCUREMENT-OPENING-STOCK-SCHEDULE.md` | The master register only flags Opening Stock? Y/N per item; the actual opening quantity, reorder point, and reorder quantity are sized in this dedicated schedule, not duplicated in the register itself. |
| China sourcing detail (spec, QC, samples, factory requirements per sourcing group) | `docs/architecture/PROCUREMENT-CHINA-PACKAGE.md` | The register only carries the China Candidate Y/N flag per item; the executable sourcing-group detail lives only here. |
| Australia sourcing detail (named suppliers, RFQ format per category) | `docs/architecture/PROCUREMENT-AUSTRALIA-PACKAGE.md` | The register only carries the Australian Source Y/N flag per item; the executable supplier-category detail lives only here. |
| Site dependency (what exactly must be measured) | `docs/architecture/PROCUREMENT-SITE-DEPENDENT-HOLD-LIST.md` | The register only flags Venue Dependent? Y/N per item; the exact measurement/confirmation requirement per category lives only here. |
| WDP dependency (what exactly WDP must confirm) | `docs/architecture/PROCUREMENT-CLINICAL-GTT-WDP-SPLIT.md` | The register only flags WDP Supplied? per item; the specific, item-by-item confirmation requirement and responsibility split lives only here. |

**If any procurement document is ever found to disagree with `MASTER-PROCUREMENT-SHOPPING-LIST.md` on item identity, quantity, specification, sourcing route, price, or Readiness, the master register wins and the other document must be corrected, not the reverse.** For opening stock, China detail, Australia detail, site dependency, and WDP dependency, the dedicated document above wins for that specific question, since it carries detail the register itself does not (and by design should not) duplicate.
